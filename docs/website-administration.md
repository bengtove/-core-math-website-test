# CoRE-Math website administration

This note records the practical information needed to maintain or recover the
CoRE-Math website. It was reviewed on 26 October 2026. Repository facts below
are verified from the working repository; Wix registration and billing details
are administrative information supplied by the site owner and should be
checked in Wix before acting on them.

## Hosting and deployment

- **Repository:** [bengtove/-core-math-website-test](https://github.com/bengtove/-core-math-website-test)
- **Publishing branch and folder:** `main`, `/ (root)`; GitHub Pages is set to
  deploy from that branch.
- **Site generator:** Jekyll, using the `jekyll-theme-primer` theme and the
  `jekyll-sitemap` plugin. The relevant configuration is
  [`_config.yml`](../_config.yml).
- **Production address and canonical base URL:**
  `https://www.africaeuropecoremath.org`. `baseurl` is intentionally empty.
- **Custom-domain file:** the root [`CNAME`](../CNAME) contains exactly
  `www.africaeuropecoremath.org`.
- **HTTPS:** the site is live over HTTPS and **Enforce HTTPS** is enabled in
  GitHub repository **Settings → Pages**. Recheck this setting whenever domain
  settings are changed.

To publish an ordinary website change, make and test the change locally,
commit it to `main`, and push `main` to `origin`. GitHub Pages then builds and
publishes the site. Check the repository’s Actions/Pages status after each
production-relevant push. Do not put credentials in the repository.

Important supporting files include [`_config.yml`](../_config.yml),
[`CNAME`](../CNAME), [`robots.txt`](../robots.txt), the layouts in
[`_layouts/`](../_layouts/), and the workflows in
[`.github/workflows/`](../.github/workflows/). `robots.txt` derives its
sitemap address from `site.url`; the sitemap is generated by `jekyll-sitemap`.

The operational workflows are documented in [Automations](automations.md).
In particular, daily event-archive rebuilding and the funding-opportunities
import depend on GitHub Actions continuing to run against this repository and
its `main` branch. The funding import requires the repository secret
`CODA_API_TOKEN`; its value must never be recorded here.

## Website analytics

The website uses [Freqo](https://freqo.eu) for anonymous usage statistics for
`africaeuropecoremath.org`. The service is administered through the Freqo
account registered with an ISP email address. It is intended to provide visitor
and page-view counts, popular pages, referring websites, country-level
geographical distribution, and related aggregate browser and device data.

The site is configured in Freqo's **Essential** mode. This is the anonymous,
cookie-free counting mode: it does not display a consent banner and does not
recognise returning visitors. Freqo states that anonymous statistics are hosted
in France and retained for 25 months. The site should continue to avoid adding
other analytics, cookies, or consent features unless a deliberate privacy
decision is made.

### Integration and maintenance

The integration was added in commit `d407577`. Its shared include is
[`_includes/freqo-analytics.html`](../_includes/freqo-analytics.html), which is
included in both [`_layouts/default.html`](../_layouts/default.html) and
[`_layouts/redirect.html`](../_layouts/redirect.html). The include emits the
deferred Freqo script only when both conditions are true:

- Jekyll is building in the `production` environment; and
- `site.url` is exactly `https://www.africaeuropecoremath.org`.

Consequently, ordinary local Jekyll development builds and previews do not
contain the tracking script. A developer should not deliberately set
`JEKYLL_ENV=production` against the production URL for a preview unless that
preview is intended to be tracked.

The tracking identifier is the public `data-site` value in the include; it is
not an account credential. To replace or remove Freqo, edit or remove that
include rather than adding code to individual pages, then commit and deploy as
usual. Keep account passwords, recovery codes and any future API credentials
outside the repository.

To view statistics, sign in to the Freqo dashboard with the ISP-administered
account, select the CoRE-Math site, and choose the required date range. The
dashboard provides its aggregate traffic views, including pages, traffic
sources, countries and devices. To exclude an administrator's own browser from
future counting, visit the live site once with `#freqo-ignore` appended to its
URL (for example `https://www.africaeuropecoremath.org/#freqo-ignore`). To
resume counting in that browser, use `#freqo-unignore`. This preference is
stored only in that browser's local storage.

### Development and live-site testing

Local development builds and previews do not load Freqo because the shared
include requires both Jekyll's `production` environment and the production
site URL. GitHub Actions builds, local-asset validation, `curl` checks and
other HTTP-only checks also do not create Freqo page views: they do not execute
the tracking JavaScript.

In contrast, an interactive browser visit to the live site can be counted.
Do not assume that an administrator's existing exclusion applies to a Codex
browser, an automated browser, a private window, or another browser profile:
each has separate local storage. Before an interactive live-site test in any
such context, open the relevant production URL with `#freqo-ignore` appended,
for example:

```text
https://www.africaeuropecoremath.org/#freqo-ignore
```

Then carry out further checks in that same browser profile. The current Freqo
script processes this hash before its tracking initialisation and saves
`freqo_ignore=true` in that profile's local storage. Do not use
`#freqo-unignore` in a test profile unless future visits from that profile are
intended to be counted. This exclusion is local to the testing browser and
does not affect genuine visitors or historical statistics.

For future Codex work, prefer non-browser checks for routine deployment
verification. When browser rendering, touch interaction, or accessibility
testing of the live site is necessary, establish `#freqo-ignore` first in the
exact browser profile used for the test and record that the visual test was
performed with analytics excluded.

### Statistics export and privacy

Freqo publicly documents CSV export for its statistics, including the
dashboard's traffic breakdowns such as pages, sources, countries and devices.
Its public pricing states that the Free plan includes all analytics, so CSV
export appears to be available there; confirm this in the account before
depending on it for a formal reporting workflow. The public documentation does
not specify the exact dashboard export controls or whether every view has a
separate export. Record any established export procedure here after it has been
confirmed in the account. Freqo states that statistics are retained for 25
months, so export periodic reports if longer historical retention is required.

The service records anonymous audience measurements in Essential mode. Freqo
states that it does not store visitors' IP addresses, track people across sites,
sell statistics or move visitor data outside France. The site has no current
privacy notice or cookie policy in the repository. Whether to add a short
privacy notice is an editorial and governance decision; consult the relevant
institutional privacy guidance before changing public wording.

## Backup and recovery

An independent Git-bundle backup is stored in Dropbox at:

`CoRE-Math/06. Communication, Dissemination, and Visibility/Website/Administration/Backups/core-math-website-2026-10-25.bundle`

Its SHA-256 checksum is stored alongside it in
`core-math-website-2026-10-25.bundle.sha256`. The bundle was created from the
canonical repository after fetching available remote refs. It records `main`
at `b1bdd7d`; no tag refs were available at the time of creation. It is
verified with `git bundle verify` and its SHA-256 checksum.

For a new backup after a significant website change, first ensure that all
material work is committed (a Git bundle does not include uncommitted or
untracked files), then run the following from a clean local checkout:

```sh
git fetch --all --tags --prune
bundle="/path/to/Dropbox/CoRE-Math/.../core-math-website-YYYY-MM-DD.bundle"
git bundle create "$bundle" --all
git bundle verify "$bundle"
shasum -a 256 "$bundle" > "$bundle.sha256"
shasum -a 256 -c "$bundle.sha256"
```

Use the existing Dropbox `Website/Administration/Backups` folder, replace the
date in the filename, and store the checksum with the bundle. Retain a small
number of dated copies. The bundle preserves the committed repository history,
branches and tags. To test or restore it elsewhere:

```sh
git clone core-math-website-YYYY-MM-DD.bundle core-math-website
cd core-math-website
git branch -a
```

If GitHub itself needed recovery, create or identify the intended repository,
add it as `origin`, push the recovered refs only after confirming the target,
then restore GitHub Pages to `main` and `/ (root)`, re-enter the custom domain,
and confirm the `CNAME`, DNS records and HTTPS setting. For a site-only
incident, first use Git history to restore a known good commit to `main` and
let GitHub Pages redeploy; do not change DNS unless the hosting endpoint has
also changed.

The bundle cannot restore GitHub Pages settings, DNS configuration, Wix
registration, repository secrets (including `CODA_API_TOKEN`), collaborator
access, or uncommitted local files. Those must be restored separately through
their respective services or from a separate documented copy.
